ATLAS / A REAL CPU + GPU DEMONSTRATION

One job. Two different teams.
Is sharing the work worth it?

Group delivery stops into four nearby areas. A CPU is a small team of versatile workers. A GPU is a large team doing similar calculations. ATLAS adjusts how much work each team receives.

RECORDED MEASUREMENT · 2026-11-24 05:43 UTC Synthetic locations · real CPU/CUDA execution

The research problem: using both processors can reduce waiting, but transferring data and coordinating them also takes time. The best split depends on the workload and machine.

1 / Here is the job

Every dot is a delivery stop. The algorithm repeatedly assigns nearby stops to the same area.

Coordinates are synthetic east–west / north–south units. This groups locations; it does not plan vehicle routes.

allocation changes in the first ATLAS trial. The GPU gets the remaining share: 30% CPU means 70% GPU.

4 / Did the answer stay correct?

Same groups. All modes.

Every trial passed a native independent reference check. Final memberships and group centers match across all execution modes and repetitions. Controller decisions were replayed.

What this proves: this input can be processed correctly while ATLAS changes the CPU/GPU work split.

What this cannot prove: general speedup, energy savings, distributed scalability or full GreenGPU acceptance.

Explain it to your classmates in 30 seconds

“We gave the computer a location-grouping job. Instead of always sending everything to the GPU, ATLAS can use both the CPU and GPU and adjust their shares. We compare the same task three ways, check the answers match, and measure the time. Sometimes sharing helps; sometimes coordination costs more. This demo shows that tradeoff on this machine.”

To show scale: run Small, Medium and Large in the launcher. Compare how the outcome changes as the job grows. These are bounded single-host sizes: 2,000, 16,000 and 64,000 stops. Each run records actual results; larger inputs are not promised to run faster.
